# 기술 선택 근거 (Technical Decision Log)

## 1. LLM 호출 방식

| 선택지 | 우리 선택 | 이유 |
|---|---|---|
| Anthropic API 직접 호출 | ❌ | 모델 고정, 비용 높음 |
| OpenAI API 직접 호출 | ❌ | 모델 고정 |
| **OpenRouter 경유** | ✅ | 단일 API로 모델 교체 자유 (gpt-oss-20b → 다른 모델 즉시 전환), 비용 최적화 가능 |
| LangChain 등 프레임워크 | ❌ | 추상화 레이어 추가 대비 이점 없음. 우리 로직이 단순해서 직접 호출이 디버깅·제어에 유리 |

## 2. 임베딩 모델

| 선택지 | 우리 선택 | 이유 |
|---|---|---|
| **OpenAI text-embedding-3-small** | ✅ | 한국어 성능 양호, 차원 수 1536으로 적당, 비용 저렴 |
| OpenAI text-embedding-3-large | ❌ | 3072차원 — 우리 데이터 규모에서 정확도 차이 미미, 비용·저장 2배 |
| Cohere embed-multilingual | ❌ | 한국어 지원하나, API 의존성 하나 더 추가됨 |
| 로컬 임베딩 (sentence-transformers) | ❌ | Vercel 서버리스 환경에서 모델 로딩 불가 |

## 3. 벡터 검색 방식

| 선택지 | 우리 선택 | 이유 |
|---|---|---|
| **인메모리 코사인 유사도** | ✅ | 4,479 청크 / 35MB — 전체 순회해도 수십ms. 추가 인프라 불필요, Vercel에 그대로 배포 |
| Weaviate | ❌ | 별도 서버 필요, 배포 복잡도 증가. 5만 청크 이상일 때 도입 가치 |
| Pinecone | ❌ | 클라우드 종속, 무료 티어 제한, 우리 규모에 과잉 |
| ChromaDB | ❌ | 로컬 실행은 가능하나 Vercel 서버리스와 비호환 |
| pgvector (PostgreSQL) | ❌ | DB 서버 관리 부담. 정적 데이터에 RDBMS 불필요 |

## 4. 리스크 계산 방식

| 선택지 | 우리 선택 | 이유 |
|---|---|---|
| LLM이 직접 계산 | ❌ | 숫자 계산 부정확, 매번 결과가 달라짐 (비결정론적) |
| **Function calling → 서버 코드 실행** | ✅ | 결정론적 계산. 동일 입력 → 동일 출력. 통계청 데이터 직접 참조하여 근거 명확 |
| 별도 계산 API 서버 | ❌ | 인프라 분리 대비 이점 없음. 같은 Next.js 앱 내에서 처리 가능 |

## 5. 가드레일 (컴플라이언스)

| 선택지 | 우리 선택 | 이유 |
|---|---|---|
| 시스템 프롬프트만으로 제어 | ❌ | LLM이 프롬프트를 100% 따르지 않음. 금지 표현 누출, 보험료 추측 등 방지 불가 |
| **시스템 프롬프트 + 사후 필터링 코드** | ✅ | 프롬프트로 1차 방어, 코드로 2차 방어 (금지표현 치환, 상품명 마스킹, 보험료 검증, 환각 감지) |
| Guardrails AI 등 외부 라이브러리 | ❌ | 한국어 금융 도메인 규칙이 없어서 커스텀이 필요. 직접 구현이 더 정확 |

## 6. 데이터 저장

| 선택지 | 우리 선택 | 이유 |
|---|---|---|
| **JSON 파일 직접 로드** | ✅ | 데이터가 정적(상품 7개, 통계 고정). 서버 시작 시 1회 로드 후 캐싱. DB 관리 오버헤드 제로 |
| PostgreSQL / MySQL | ❌ | 정적 데이터에 CRUD 불필요. DB 서버 유지비용 추가 |
| MongoDB | ❌ | JSON 그대로 쓸 수 있지만, 파일로 읽는 것과 차이 없음 |
| Supabase | ❌ | 무료 티어에서 사용 가능하나, 추가 의존성 대비 이점 없음 |

## 7. 프론트엔드 + 배포

| 선택지 | 우리 선택 | 이유 |
|---|---|---|
| **Next.js (App Router) + Vercel** | ✅ | 프론트+API를 단일 프로젝트로 관리. Vercel 무료 배포. SSR/서버리스 함수 기본 지원 |
| React + Express 분리 | ❌ | 프론트/백 각각 배포 필요. 인프라 관리 2배 |
| Streamlit | ❌ | 프로토타이핑엔 빠르지만 커스텀 UI 제한, 프로덕션 배포 어려움 |
| Gradio | ❌ | ML 데모용. 보험 상담 같은 복잡한 다단계 UI에 부적합 |

## 8. 대화 흐름 제어

| 선택지 | 우리 선택 | 이유 |
|---|---|---|
| LLM 자율 판단 | ❌ | Stage 건너뛰기, 루프, 빈 응답 발생 |
| 상태 머신 (클라이언트) | ❌ | 클라이언트에서 stage 올리면 LLM과 동기화 어려움 |
| **시스템 프롬프트 + tool_choice 강제 + 서버 자동 승격** | ✅ | 3중 제어. Stage 2에서 tool_choice로 리스크 툴 강제 호출, risk_map 완료 후 자동으로 Stage 3 승격 |

## 9. 평가 (Eval)

| 선택지 | 우리 선택 | 이유 |
|---|---|---|
| 수동 테스트만 | ❌ | 반복 불가, 회귀 감지 어려움 |
| **규칙 기반 자동 평가 (evaluator.ts)** | ✅ | 12개 규칙으로 대화 로그 자동 채점. CLI로 즉시 실행 가능. 변경 후 회귀 확인 용이 |
| LLM-as-judge | ❌ | 비용 발생, 평가 기준이 비결정론적. 규칙 기반이 재현 가능하고 명확 |
| 외부 eval 프레임워크 (promptfoo 등) | ❌ | 셋업 오버헤드 대비 우리 규모에 과잉 |

## 요약: 기술 선택 원칙

1. **데이터 규모에 맞는 적정 기술** — 4,479 청크에 벡터 DB는 과잉, 상품 7개에 RDBMS는 과잉
2. **LLM을 신뢰하지 않는 설계** — 계산은 코드로, 표현은 필터로, 흐름은 강제로
3. **단일 배포 단위** — Next.js 하나로 프론트+백엔드+RAG, Vercel 한번에 배포
4. **외부 의존성 최소화** — 프레임워크·DB·벡터DB 없이, 필요한 것만 직접 구현
